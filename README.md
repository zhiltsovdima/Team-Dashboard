# Team-Dashboard
## О проекте

**TeamDashboard** — тестовое мобильное приложение, созданное для экспериментов с архитектурой **[The Composable Architecture (TCA)](https://github.com/pointfreeco/swift-composable-architecture)**. Основная цель проекта — исследовать возможности TCA, научиться использовать навигацию, зависимости и другие основные фишки этой архитектуры. По этой причине UI - максимально примитивный, а подгрузка данных часто использует обычные моки.

На данный момент проект находится в активной разработке
## Почему TCA?
Классические архитектуры вроде MVVM как будто не совсем в духе философии SwiftUI. TCA — это свежий взгляд, который переосмысливает привычные подходы. Меня зацепила её строгость, четкий контроль над данными и очень приятное тестирование. Хотелось попробовать новый подход.

## На что можно посмотреть?

Можно посмотреть на сетевой модуль Core/Network и моковый сервис-зависимость к нему RemoteTeamService. В этот раз я попробовал сделать этот слой еще более масштабируемым и кастомизированным под различные условия. Боевое крещение еще не прошел. Отдельным моментом хочу упомянуть сетевой логгер NetworkLogger с приятной удобной индикацией. Разработал его под себя, но не без слабого места(можно упустить скрытие важных параметров).  

Можно посмотреть на слой CoreData, в этот раз я тоже попробовал что-то новое и сделал многоуровневую реализацию стека для управления контекстами.

Переходим к фишкам от pointfree

При запуске приложения пускаем загрузочный экран. Допустим нам нужно подтянуть какие-то важные данные конфиги. Сделал IntroDataService, который отдает данные, попробовав новый подход, который предлагают создатели TCA.

Протестировал смену флоу от экрана загрузки к основному экрану приложения

На главном экране внедрил таб бар

Экран Dashboard, имеет несколько состояний, загружает асинхронно данные(задачки для пользователя). 

Попробовал реализовать навигацию стека - показ детально выбранной задачи. И в списке задач и в детальном отображении можно кликнуть по кнопке, которая меняет состояние задачи на выполнил/не выполнил. Важно было протестировать изменение состояния одного и того же объекта с разных экранов.

Хотел еще протестировать показ алертов. 
В документации TCA предлагают в каждом нужном reducer внедрять какие алерты должен показывать сопутствующий экран. Не знаю, мне такой подход вызывает сомнение. В реальном проекте получится слишком много дублирования на мой взгляд. Мне кажется централизованная система была бы лучше. Каждый дочерний reducer посылает сигнал главному reducer, тот уже обрабатывает и показывает нужный алерт. Можно было бы для главного reducer составить специальный reducer который бы как раз отвечал за логику показа таких сообщений. Пока еще не доделал этот слой.

Немаловажно - попробовал тестирование. Выглядит прикольно. Лайк.

## Размышления
Кривая обучения TCA все-таки серьезная. Насколько эта архитектура может стать распространненной практикой - большой вопрос. Искать подходящих разработчиков будет сложнее. Но мне, как минимум, было любопытно самому в это вникнуть, изучить и попробовать на практике.
